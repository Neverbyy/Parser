# Отзывы организаций из Яндекс.Карт

Приложение из двух экранов: вход и страница настроек, куда вставляется ссылка на карточку организации в Яндекс.Картах. После сохранения подтягиваются средний рейтинг, раздельные счётчики оценок и отзывов и сами отзывы с постраничной навигацией по 50 штук.

Официального API у Яндекса нет — данные добываются парсингом, и это центральная часть работы.

```
backend/    Laravel 13 — API и парсер
frontend/   Vue 3 + TypeScript — SPA
```

Подробности по частям: [backend/README.md](backend/README.md), [frontend/README.md](frontend/README.md).

---

## Запуск

### Docker

```bash
docker compose up
```

- SPA — <http://localhost:5173>
- API — <http://localhost:8000>
- Вход: **demo@example.com** / **password** (регистрации нет, пользователь заводится сидером)

Зависимости, `.env`, ключ приложения, файл базы, миграции и сид создаются при старте автоматически. Первый запуск занимает пару минут — ставятся composer- и npm-пакеты; дальше они лежат в томах.

Если порты заняты:

```bash
FRONTEND_PORT=5174 BACKEND_PORT=8001 docker compose up
```

### Без Docker

Нужны PHP ≥ 8.3 и Node ≥ 20.

```bash
cd backend && composer setup && php artisan serve --host=127.0.0.1 --port=8000
cd frontend && npm install && npm run dev
```

## Подход к парсингу и обход защиты

Отзывы на карточке догружаются скриптом по мере прокрутки, поэтому напрашивается headless-браузер. Я выбрал другое: **разобрал внутренние запросы карточки** — за прокруткой стоит обычный GET, который можно повторить напрямую.

| | Внутренние JSON-запросы | Headless-браузер |
|---|---|---|
| 600 отзывов | **~10 секунд**, 14 запросов | минуты: 12 подгрузок с ожиданиями |
| Зависимости | только PHP | Chromium ~150 МБ + драйвер |
| Данные | готовый типизированный JSON | выборка по селекторам |
| Устойчив к антиботу | хуже: обычный HTTP-клиент | лучше: настоящий отпечаток браузера |
| Хрупок к | подписи `s`, структуре SSR-состояния | вёрстке и селекторам |

**Что даёт защиту и как она обходится:**

1. **Подпись запроса.** Эндпоинт `/maps/api/business/fetchReviews` без параметра `s` отвечает 400 с пустым телом. Алгоритм восстановлен из клиентского бандла карт: параметры сортируются по ключу без учёта регистра, кодируются по RFC 3986, от строки считается djb2-xor в 32 битах. Закреплён юнит-тестом с контрольным вектором, снятым с живого принятого запроса.
2. **Куки сессии.** Карточка и API ходят через один cookie-jar: без кук, выданных на первой странице, API отвечает 400 даже с верной подписью.
3. **Темп.** Паузы со случайной добавкой между страницами, один User-Agent и один прокси на весь проход, растущий бэкофф при сбоях.

Ключевая находка: **Яндекс жёстко обрезает выдачу на 600 отзывах** (12 страниц по 50) независимо от их реального количества — проверено на карточках с 5858, 2632 и 778 отзывами. Отсюда и ориентир «примерно 600» из задания.

Разбор алгоритма подписи, анатомия карточки и остальные находки — в [backend/README.md](backend/README.md).

## Дополнительные требования

### 1. Устойчивость к смене разметки

Опаснее всего не падение, а **тихий успех**: запросы прошли, ошибок нет, статус `ready`, отзывов ноль — снаружи неотличимо от организации, у которой отзывов и правда нет. Поэтому парсер проверяет себя на каждом шаге:

| Что сломалось | Как обнаруживается | Код |
|---|---|---|
| Убрали блок SSR-состояния или он не разбирается | нет `state-view` / невалидный JSON | `markup_changed` |
| Переехали ключи доступа | нет `csrfToken` или `sessionId` | `markup_changed` |
| Ссылка ведёт не на организацию | в состоянии нет карточки `type: business` | `organization_unavailable` |
| **Переименовали поля отзыва** | записи пришли, но **ни одна** не разобралась | `markup_changed` |
| **Сломался обход целиком** | карточка обещает N > 0 отзывов, собрано **ноль** | `markup_changed` |
| Эндпоинт отвечает не JSON | тело не разбирается | `empty_response` |
| Сменился алгоритм подписи | все запросы получают 400 → собрано ноль → строка выше | `markup_changed` |
| Включилась защита от ботов | в ответе `type: captcha` | `captcha` |
| Придержали адрес | 403 или 429 | `blocked` |

Две выделенные строки — защита от тихой пустоты. Вторая сверяет **два независимых источника**: счётчик берётся из карточки, отзывы — из API; каждый шаг по отдельности «успешен», но расхождение означает поломку. Организация без отзывов при этом поломкой не считается — счётчик подтверждает, что их нет. Всё покрыто тестами (`ParsingResilienceTest`).

Куда попадает сигнал: **лог** (`Log::warning` с кодом, номером попытки, идентификаторами), **база** (`status = failed`, человекочитаемый `error_message`), **API** (свой HTTP-код на каждый тип), **интерфейс** (текст ошибки и кнопка «Попробовать снова»).

Плюс два ранних предупреждения: юнит-тест подписи с контрольным вектором и живой тест `php artisan test --group=live`, проверяющий совместимость с настоящим Яндексом по требованию.

### 2. Обоснование подхода к парсингу

Сравнение, плюсы и риски — в разделе [«Подход к парсингу»](#подход-к-парсингу-и-обход-защиты) выше. Коротко: выбраны внутренние запросы ради скорости на порядок и отсутствия тяжёлых зависимостей; плата — привязка к недокументированному контракту.

Главная точка отказа — **алгоритм подписи `s`**: при его смене встанут все запросы отзывов. Чинится повторным чтением бандла; обнаруживается сразу (см. пункт 1). Вторая по значимости — структура SSR-состояния; агрегаты подстрахованы schema.org-микроразметкой как вторым источником, а вот `csrfToken` и `sessionId` дублировать нечем. Протухание токена уже обработано: парсер ловит новый токен в теле ответа и повторяет запрос один раз.

Если Яндекс ужесточит защиту, разумный шаг — не переписывать всё на Playwright, а **гибрид**: браузер поднимается один раз за куками и токенами, постраничный обход остаётся на быстрых HTTP-запросах. Заменить пришлось бы только `YandexMapsClient` и `CardPageParser`.

### 3. Масштаб и фоновая обработка

~50 филиалов по ~600 отзывов — это около 700 запросов и больше десяти минут работы. Синхронно в HTTP-запросе такое не делается, поэтому разбор одной организации оформлен как job с самого начала.

**Реализовано:**

- **Очередь.** По умолчанию `QUEUE_CONNECTION=sync`, чтобы не требовать воркер. Для фона — `database` и `php artisan queue:work`; **код при этом не меняется**, и бэкенд, и фронт работают через поле `status`.
- **Повторы.** `tries = 3`, растущий бэкофф `[30, 120, 300]` секунд, `timeout = 300`. Повторяются только сбои, которые могут пройти сами (обрыв, пятисотка, капча, временная недоступность); неверная ссылка и смена формата фиксируются сразу. По исчерпании попыток срабатывает `failed()` и организация получает `status = failed` с причиной.
- **Без наложения.** `WithoutOverlapping` по организации: два прохода не пишут в одни строки.
- **Прогресс.** Парсер отдаёт число собранных отзывов после каждой страницы, job пишет его в `fetched_reviews_count` по ходу работы. Фронт и так опрашивает организацию, пока статус `parsing`, и показывает «Собираем отзывы — уже 350…». Отдельный канал не понадобился.
- **Массовый обход.** `php artisan yandex:parse-all --gap=45` раскладывает задачи по времени, а не выстреливает разом. Для 50 филиалов при шаге 45 с обход займёт около 37 минут — размазать нагрузку важнее, чем успеть быстро.

**Добавил бы на реальном объёме:** расписание (`Schedule::command(...)->dailyAt('04:00')`), отдельную очередь с одним воркером как ограничитель параллелизма, `Bus::batch()` ради прогресса по всему обходу и отмены целиком, `RateLimited`-middleware на весь обход.

### 4. Анти-бан на объёме

| Приём | Как сделано |
|---|---|
| Троттлинг внутри разбора | пауза между страницами, `YANDEX_REQUEST_DELAY_MS` |
| Дрожание интервала | случайная добавка 0–400 мс: ровный интервал — первое, по чему узнают автоматику |
| Троттлинг между организациями | шаг раскладки задач, `YANDEX_ORGANIZATION_GAP_SECONDS` |
| Ротация User-Agent | пул в `config/yandex.php`, один UA **на весь проход** |
| Ротация прокси | список в `YANDEX_PROXIES`, один адрес **на весь проход** |
| Бэкофф при сбое | 30 с → 2 мин → 5 мин |
| «Нас забанили» | 403/429 → отдельный `blocked`; капча → `captcha` |

Про ротацию важно: UA и прокси закрепляются **за проходом целиком**, а не меняются между запросами. Внутри сессии Яндекс уже выдал куки конкретному браузеру с конкретного адреса — браузер, который посреди сессии переименовался или переехал в другую страну, подозрительнее постоянного. И 429 намеренно **не** входит в список кодов для автоповтора: на «слишком часто» правильный ответ — отступить, а не переспросить через полсекунды.

Блокировка отличается от прочих ошибок кодом, попадает в лог и в `error_message`, задача уходит на повтор с растущей паузой, а обход остальных организаций не останавливается.

**Добавил бы:** предохранитель (несколько блокировок подряд — флаг в кеше и пауза на полчаса для всех задач), пул прокси с карантином для получивших 403, оповещение в мессенджер вместо молчаливого накопления `failed`, адаптивный темп (после блокировки паузы вдвое длиннее, после серии успехов — осторожно назад).

### 5. Идемпотентность и история изменений

Повторный разбор **обновляет записи, а не создаёт дубли**. Отзывы пишутся через `upsert` по ключу `(organization_id, yandex_review_id)`: существующий обновляется на месте вместе со своим `created_at` — видно, когда отзыв появился у нас впервые; новый добавляется; тот, которого Яндекс больше не отдаёт, удаляется, чтобы таблица соответствовала последнему снимку.

История агрегатов — таблица `organization_snapshots` (`rating`, `ratings_count`, `reviews_count`, `fetched_reviews_count`, `created_at`). Снимок пишется **только при изменении значений**, иначе ежедневный разбор засорял бы её одинаковыми строками. «Стало → было» получается одним запросом:

```sql
SELECT created_at, rating, ratings_count, reviews_count
FROM organization_snapshots
WHERE organization_id = ? ORDER BY created_at DESC LIMIT 2;
```

Историю правок **каждого отзыва** не реализовывал — в объёме задания это избыточно. Модель достраивается одной таблицей:

```
review_revisions
  review_id     FK на reviews
  rating, text  значения на момент снимка
  content_hash  хеш (rating, text) — по нему решается, менялось ли что-то
  created_at
```

Запись по тому же принципу: при разборе считается хеш, сравнивается с последней ревизией, строка добавляется только если он другой. Для 50 филиалов это 30 000 строк на первый проход и единицы на последующие.

## Что грузим сразу, а что подкачиваем

Развилка: ходить в Яндекс на каждое переключение страницы или разобрать карточку один раз и раздавать отзывы из своей базы. **Выбрано второе.**

- **Скорость.** Проход парсера — 10–20 секунд, выдача 50 отзывов из базы — миллисекунды. Иначе клик по «странице 2» стоил бы двадцати секунд ожидания уже полученных данных.
- **Нагрузка на источник.** Один разбор — 14 запросов. Умножать их на каждое листание — прямая дорога к блокировке.
- **Стабильность пагинации.** Выдача Яндекса живая: пока человек листает, туда добавляются отзывы и окно сдвигается. Свой снимок неподвижен — тест проверяет, что страницы не пересекаются.
- **Живучесть.** Если Яндекс лёг или показал капчу, приложение показывает последний успешный снимок.

Все 600 разом на фронт тоже не отдаются: задание требует постраничной навигации, а 600 узлов в DOM на ровном месте ни к чему. Снимок лежит в БД, а не в кеше, потому что нужна сортировка и порционная выдача по индексу `(organization_id, published_at)`. Плата — данные устаревают, поэтому в интерфейсе видно `parsed_at` и есть кнопка «Обновить данные». На фронте поверх лежит второй слой кеша (TanStack Query): возврат на предыдущую страницу — мгновенный и без запроса.

## Что доделал бы, имея больше времени

- **E2E-тесты.** Логика покрыта 75 тестами на бэкенде и 49 на фронте, но браузерного сценария (Playwright) нет
- **Circuit breaker и здоровье прокси** — см. пункт 4.
- **`review_revisions`** — полная история правок отзывов, см. пункт 5.
- **Наблюдаемость.** Метрики длительности разбора, доли сбоев по кодам и возраста данных; сейчас есть только логи.
- **Хранение архива.** Отзывы, вытесненные за пределы шестисот, сейчас удаляются ради согласованности со снимком. Для мониторинга репутации их логичнее накапливать — это отдельное решение с отдельной семантикой счётчиков.
