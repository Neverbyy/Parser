# Фронтенд

Vue 3 (Composition API, `<script setup>`) + TypeScript, Vite. Два экрана: вход и страница настроек с данными организации.

Полное описание проекта — в [README проекта](../README.md).

## Запуск

Сначала поднимите бэкенд на `http://localhost:8000` (см. [backend/README.md](../backend/README.md)), затем:

```bash
npm install
npm run dev
```

Откроется `http://localhost:5173`. Вход: `demo@example.com` / `password`.

## Состояние: два разных вида

Ключевое архитектурное решение — разделить состояние по природе, а не по слоям.

| | Где живёт | Что именно |
|---|---|---|
| Клиентское | **Pinia** (`stores/auth.ts`) | кто вошёл, номер открытой страницы |
| Серверное | **TanStack Query** (`queries/`) | организация, отзывы, статусы запросов |

Почему так: организация и отзывы — не состояние приложения, а копия того, что лежит на сервере. Складывать их в Pinia значит вручную писать то, что Query уже умеет: кеш, признаки загрузки и ошибки, дедупликацию, инвалидацию, сохранение предыдущей страницы при листании.

В Pinia остаётся только личность пользователя — её guard роутера должен получать синхронно, ещё до первого рендера.

Побочный эффект, который оказался особенно уместен: у организации на бэкенде есть поле `status`, и запрос сам опрашивает сервер, пока разбор не закончится.

```ts
refetchInterval: (query) => (isInProgress(query.state.data?.status) ? 2000 : false)
```

Сейчас бэкенд работает на синхронной очереди и отвечает уже готовым результатом, так что до опроса дело не доходит. Но если переключить `QUEUE_CONNECTION` на фоновую очередь, интерфейс продолжит работать **без единой правки** — он и так ориентируется на `status`.

## Аутентификация

Sanctum в режиме SPA: обычная сессионная кука, без токенов.

Vite проксирует `/api` и `/sanctum` на бэкенд, поэтому браузер видит один origin. Это снимает и CORS, и самую частую проблему связки Sanctum с SPA — ошибку 419 из-за кросс-доменных кук.

CSRF-куку никто не запрашивает вручную: интерцептор в `api/client.ts` сам сходит за ней перед первым изменяющим запросом, и параллельные запросы поделят один поход на сервер.

Все ошибки — валидация, сбой парсера, обрыв сети — приводятся к одной структуре `ApiError`, поэтому компоненты не разбирают ответы axios.

## Состояния загрузки и ошибок

Видимы везде, где что-то может пойти не так:

- вход — блокировка формы, ошибки под полями, отдельная плашка для сетевых сбоев;
- сохранение ссылки — валидация в форме до запроса, ошибка сервера под полем, предупреждение про 10–20 секунд ожидания;
- разбор — индикатор при `parsing`, причина и кнопка повтора при `failed`;
- отзывы — скелет при первой загрузке, приглушение списка при листании, пустое состояние, ошибка с кнопкой «Повторить».

## Структура

| Путь | Что это |
|---|---|
| `api/` | axios-клиент (CSRF, нормализация ошибок) и функции запросов |
| `queries/` | обёртки TanStack Query: организация, отзывы, вход |
| `stores/auth.ts` | Pinia: текущий пользователь |
| `router/` | маршруты и guard'ы |
| `views/` | два экрана |
| `components/` | компоненты предметной области и `ui/` — примитивы |
| `utils/` | форматирование (включая русскую плюрализацию) и валидация ссылки |
| `types/api.ts` | контракт с бэкендом |

Стили — свой CSS в `<style scoped>` на CSS-переменных из `styles/main.css`; тёмная тема поддержана через `prefers-color-scheme`.

## Команды

```bash
npm run dev        # дев-сервер с прокси на бэкенд
npm run build      # проверка типов и сборка
npm run typecheck  # только проверка типов
npm test           # 49 тестов
```

Тесты покрывают форматирование и валидацию ссылки, а также оба экрана целиком: вход с ошибками полей и сети, сохранение ссылки, раздельные счётчики оценок и отзывов, отображение автора/даты/текста/оценки, постраничную навигацию и состояния `parsing` и `failed`. Слой `api/` в них подменён — в сеть тесты не ходят.
